## 1) Técnicas de extração (o “como”)

Extração de fontes de dados ====**não eletrônicas**====, **====estruturadas====**, **====semiestruturadas====** e ====**não estruturadas====.**
### 1.1) Extração por consulta (Query-based / Pull)

Você “puxa” os dados fazendo consulta.

- Ex.: SQL em PostgreSQL, consulta em views, endpoints REST

**Quando usar:** bancos relacionais, data warehouses, algumas APIs.

✅ Vantagens: simples, controlável  
⚠️ Riscos: pode pesar no sistema transacional; precisa incremental bem definido

---

### 1.2) Extração por arquivo (File-based / File drop)

O sistema gera arquivos (CSV/JSON/Parquet) e você consome.

- Ex.: export diário para S3/Drive/FTP

**Quando usar:** integrações com sistemas legados, rotinas batch.

✅ Vantagens: desacopla do sistema origem  
⚠️ Riscos: mudanças no formato quebram pipeline; versionamento do schema é crucial

---

### 1.3) Extração incremental (Delta load)

Extrair apenas o que mudou desde a última carga. Estratégias:

- `updated_at > last_run`
- chave incremental (id crescente)
- snapshots + diff (quando não há `updated_at`)

✅ Vantagens: rápido e barato  
⚠️ Riscos: `updated_at` ruim, timezone, registros atualizados “atrasados”

---

### 1.4) CDC — Change Data Capture (mais avançado)

Captura mudanças direto do log do banco (insert/update/delete).

- Exemplos de ferramentas: Debezium, AWS DMS, Kafka Connect

✅ Vantagens: alta confiabilidade e near real-time  
⚠️ Riscos: mais complexo de operar; exige governança de esquema

---

### 1.5) Extração por eventos / streaming

Dados chegam continuamente.

- Kafka, Pub/Sub, Kinesis

✅ Vantagens: baixa latência  
⚠️ Riscos: duplicidade, ordenação de eventos, gestão de offsets

---

## 2) Técnicas “obrigatórias” em qualquer extração robusta

### 2.1) Checkpoint (marco de progresso)

Guardar “onde parou” para continuar sem duplicar:

- timestamp, id, cursor, offset

### 2.2) Idempotência

Rodar 2x não pode duplicar dados.

- dedupe por chave
- upsert/merge no destino
- controle por `run_id`

### 2.3) Observabilidade

- logs (linhas, tempo, erros)
- métricas e alertas (volume anormal, atraso, falha)

### 2.4) Qualidade mínima na entrada

Validações rápidas antes de transformar:

- schema esperado
- chaves não nulas
- ranges básicos

## 3) Ferramentas para extração (o “com o quê”)

Vou agrupar por cenário (pra ficar fácil de memorizar):

### 3.1) Bancos relacionais (SQL)

- **SQL puro** (scripts)
- **Python + connectors** (psycopg2, sqlalchemy)
- **Airflow/Prefect/Dagster** (para orquestrar)
- **dbt** (mais para transformação, mas depende do fluxo ELT)

### 3.2) APIs (REST/GraphQL)

- **Python (requests/httpx)** + paginação + retries
- **Postman** (explorar e testar endpoints; não é ideal para produção)
- **SDKs oficiais** (quando existem)

### 3.3) Arquivos (CSV/Excel/Parquet)

- **Python (pandas, pyarrow)**
- **S3/GCS CLI** e bibliotecas
- **Ferramentas de ingestão** (dependendo do cloud)

### 3.4) CDC e streaming

- **Debezium** (CDC open source)
- **Kafka Connect**
- **AWS DMS**
- **Pub/Sub / Kinesis** (eventos)

### 3.5) Ferramentas “no-code/low-code” (integrações rápidas)

- Fivetran, Stitch, Airbyte (conectores prontos) ✅ rápido pra começar  
    ⚠️ custo e limites; precisa governança e qualidade do mesmo jeito

---

## 4) Como escolher a técnica/ferramenta (regra simples)

- DB relacional + batch diário → **SQL/Python + incremental (`updated_at`)**
- API SaaS com limites → **Python + paginação + cursor + retries**
- Alto volume e near real-time → **CDC/streaming**
- Time pequeno e urgência → **Airbyte/Fivetran** + checks de qualidade
- Sistema legado que exporta arquivos → **file drop** + validação de schema

---

## 📋 Resumindo

- Técnicas principais: **query, file drop, incremental, CDC, streaming**
- Extração “de verdade” precisa: **checkpoint, idempotência, logs, validação**
- Ferramentas dependem do cenário: DB (SQL/Python), API (requests + retries), CDC (Debezium/DMS), no-code (Airbyte/Fivetran)
