## Introdução

A **DDL (Data Definition Language)** é a parte da SQL que **define a estrutura** do banco: bancos de dados, tabelas, colunas, chaves e restrições. Nada de dados — só o "esqueleto".

Este guia segue a ordem real de trabalho: **criar o banco → criar as tabelas → conferir → proteger com chaves → tratar relações N:N**.

⚠️ **Regra de ouro:** siga sempre a ordem **entidades fortes → entidades fracas → tabela associativa**. Inverter gera erro de violação de chave estrangeira.

---
## 1. Criar o Banco

```sql
CREATE DATABASE nome_do_banco;
```

**Observação importante:** no Oracle, na prática, você também cria o **tablespace** (onde os dados ficam fisicamente) e o **usuário** (o "banco lógico"). Para estudo, o `CREATE DATABASE` já resolve.

**Analogia:** o tablespace é o **terreno**, e o usuário é o **dono do terreno** com as chaves de acesso.

---

## 2. Criar as Tabelas (Entidades)

Antes de escrever o comando, pense no **modelo lógico**: cada **entidade** vira uma **tabela**, cada **atributo** vira uma **coluna**.

```sql
CREATE TABLE dept1 (
    deptno NUMBER(2),
    dname  VARCHAR2(14),
    loc    VARCHAR2(10)
);
```

**Tipos de dados mais usados no Oracle:**

|Tipo|O que armazena|
|---|---|
|`NUMBER(n)`|Número inteiro|
|`NUMBER(n,d)`|Número decimal|
|`VARCHAR2(n)`|Texto|
|`DATE`|Data|

**Boas práticas:**

- Palavras reservadas em **MAIÚSCULAS**; nomes de objetos em **minúsculas**
- Use indentação para legibilidade (não afeta a execução)
- Todo comando termina com **`;`**
---

## 3. Conferir a Estrutura

```sql
DESCRIBE dept1;
```

Forma curta:

```sql
DESC dept1;
```

Mostra cada coluna, seu tipo e se aceita nulo. É só leitura — não altera nada.

---

## 4. Adicionar PK e FK (integridade)

**Chave Primária (PK)** — identifica cada registro:

```sql
ALTER TABLE dept1 ADD CONSTRAINT pk_deptno PRIMARY KEY (deptno);
```

**Chave Estrangeira (FK)** — liga tabelas:

```sql
ALTER TABLE pedido ADD CONSTRAINT fk_dept
FOREIGN KEY (id_dept) REFERENCES dept1(deptno);
```

💡 **Dica de especialista:** antes de adicionar a PK, garanta que a coluna **não tem nulos nem valores duplicados**. Se tiver, o comando falha.

💡 **Sempre nomeie as constraints** (`pk_deptno`, `fk_dept`). Isso facilita a manutenção e deixa as mensagens de erro do banco muito mais claras.

---
## 5. Caso N:N — Tabela Associativa

Quando duas entidades se relacionam em **muitos-para-muitos** (um professor leciona várias disciplinas e uma disciplina tem vários professores), o banco **não aceita a relação direta**. É preciso criar uma **tabela associativa**.

### **Passo 1 — criar as entidades:**

```sql
CREATE TABLE PROFESSOR (COD_PROF NUMBER(2), NOME_PROF VARCHAR2(50));
CREATE TABLE DISCIPLINA (COD_DISC NUMBER(3), NOME_DISC VARCHAR2(50));
```

### **Passo 2 — criar a tabela associativa:**

```sql
CREATE TABLE PROF_DISC (COD_PROF NUMBER(2), COD_DISC NUMBER(3));
```

### **Passo 3 — adicionar as PKs das entidades:**

```sql
ALTER TABLE PROFESSOR ADD CONSTRAINT PK_COD_PROF PRIMARY KEY (COD_PROF);
ALTER TABLE DISCIPLINA ADD CONSTRAINT PK_COD_DISC PRIMARY KEY (COD_DISC);
```

### **Passo 4 — PK composta na associativa:**

```sql
ALTER TABLE PROF_DISC ADD CONSTRAINT PK_CODS PRIMARY KEY (COD_PROF, COD_DISC);
```

### **Passo 5 — FKs ligando a associativa às origens:**

```sql
ALTER TABLE PROF_DISC ADD CONSTRAINT FK_COD_PROF FOREIGN KEY (COD_PROF) REFERENCES PROFESSOR(COD_PROF);
ALTER TABLE PROF_DISC ADD CONSTRAINT FK_COD_DISC FOREIGN KEY (COD_DISC) REFERENCES DISCIPLINA(COD_DISC);
```

**Analogia:** a tabela associativa é a **lista de presença** de um curso. Sozinha, a lista de alunos e a lista de aulas não dizem quem esteve em qual aula — é a lista de presença que registra essa ligação.

---
## ⚠️ Atenção Importante

**Violação de chave primária**

- Ocorre ao inserir um valor de PK que já existe
- Ou ao tentar criar PK em coluna com nulos ou duplicados

**Violação de chave estrangeira**

- Ocorre ao inserir um valor de FK que **não existe** na tabela referenciada
- Ocorre ao criar a associativa **antes** das entidades fortes existirem
- Ocorre ao tentar excluir uma tabela que ainda é referenciada por FKs

**Dependências**

- Nem toda constraint pode ser adicionada se os dados existentes já violarem a regra
- `ALTER TABLE ... DROP CONSTRAINT` exige saber o **nome** da constraint

**Boas práticas antes de rodar**

- Confirme o nome da tabela e da constraint
- Verifique se a coluna está limpa (sem nulos/duplicados) antes de virar PK
- Respeite a ordem: fortes → fracas → associativas

---
## 📋 Resumo Final

|Comando|Função|Observações importantes|
|---|---|---|
|`CREATE DATABASE`|Cria o banco|No Oracle, na prática envolve tablespace + usuário|
|`CREATE TABLE`|Cria a tabela (colunas + tipos)|Pense no modelo lógico antes|
|`DESCRIBE` / `DESC`|Mostra a estrutura da tabela|Só leitura, não altera nada|
|`ALTER TABLE ... ADD CONSTRAINT`|Adiciona PK, FK, UNIQUE, CHECK|Sempre nomeie a constraint|
|`PRIMARY KEY`|Identifica o registro|Sem nulos e sem duplicados|
|`FOREIGN KEY`|Liga tabelas (integridade referencial)|O valor precisa existir na tabela referenciada|
|Tabela associativa (N:N)|Resolve relação muitos-para-muitos|PK composta pelas duas FKs|

**Regra de ouro:** entidades fortes primeiro, associativa por último — evita erro de violação de chave estrangeira.

---
## Resumindo

- **DDL estrutura o banco**, não os dados
- Fluxo correto: `CREATE DATABASE` → `CREATE TABLE` → `DESCRIBE` → `ALTER TABLE ADD CONSTRAINT`
- **PK** identifica (única, não nula); **FK** relaciona (precisa apontar para uma PK existente)
- **N:N** sempre exige tabela associativa com **PK composta**
- **Nomear constraints** e **respeitar a ordem de criação** evita a maior parte dos erros
