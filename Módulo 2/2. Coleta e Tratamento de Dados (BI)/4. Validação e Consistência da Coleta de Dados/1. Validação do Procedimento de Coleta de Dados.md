## O que é “validação do procedimento de coleta”?

É checar se o jeito que você está coletando dados (fonte → extração → staging/raw) está **correto, completo e repetível**.

Não é só validar o “dado”. É validar o **processo**:

- se está coletando **o que deveria**
- no **tempo certo**
- sem **perdas** e sem **duplicar**
- com **rastreabilidade** (dá pra auditar)

---

## O que deve ser validado na coleta (checklist essencial)

### 1) Validação da fonte e do acesso

- A fonte é a **correta**? (tabela certa, endpoint certo, aba certa)
- O acesso tem **permissão de leitura** adequada?
- Existe risco de coletar de ambiente errado (dev vs prod)?

**Exemplo:** extrair dados do ERP “homologação” por engano → dashboard fica bonito, mas falso.

---

### 2) Validação de completude (veio tudo?)

- Contagem de registros vs esperado
- Campos críticos não podem estar vazios (PK, datas, status)
- Verificar “buracos” no tempo (dias sem dados)

**Exemplo (ETL diário):** ontem tinha 50 mil linhas, hoje veio 3 mil → alerta.

---

### 3) Validação de consistência (faz sentido?)

- Datas coerentes (fim não pode ser antes do início)
- Domínios válidos (status ∈ {ABERTO, FECHADO, CANCELADO})
- Relacionamentos (FK existe? id_vaga existe na dim_vaga?)

**Exemplo:** `data_contratacao < data_abertura_vaga` → regra quebrada.

---

### 4) Validação de duplicidade (não pode duplicar)

- Checar duplicatas na chave natural
- Definir estratégia de idempotência (rodar 2x sem duplicar)
- Verificar se incremental não está reprocessando sem dedupe

**Exemplo:** API retorna mesmos registros em páginas diferentes → duplicação silenciosa.

---

### 5) Validação de incrementalidade / checkpoint (coleta “do jeito certo”)

- O `last_run` (checkpoint) está sendo atualizado só quando a carga termina OK?
- Existe “janela de segurança” (lookback) para eventos atrasados?
- A extração captura updates/deletes quando necessário?

**Exemplo:** usar `updated_at` mas ele não muda quando há alteração → você perde updates.

---

### 6) Validação de rastreabilidade (auditoria)

Guardar metadados junto com os dados extraídos:

- `run_id`
- `ingestion_timestamp`
- `source_system`
- `source_file` / `endpoint`
- quantidade de linhas extraídas

**Por quê isso importa?** Porque quando alguém pergunta “de onde veio esse número?”, você responde com evidência.

---

## Como isso cai em ETL/BI: regras de ouro

- **Staging/raw não é histórico garantido** (a menos que você defina retenção).  
    Histórico normalmente vem de **camada raw/bronze particionada** + **logs de execução**.
- Toda coleta precisa ter:
    - **validação mínima**
    - **logs**
    - **alertas** (volume, atraso, falhas)
    - **mecanismo de reprocessamento**

---

## Exemplos rápidos (bem práticos)

### Exemplo 1 — Coleta de planilha

Validações:

- colunas obrigatórias existem?
- data no formato certo?
- linhas de “TOTAL” foram ignoradas?
- duplicidade por `id + data`?

### Exemplo 2 — Coleta de banco relacional

Validações:

- consulta usa índice (não derruba o transacional)?
- incremental por `updated_at` funciona?
- contagem de linhas por dia está estável?

### Exemplo 3 — Coleta de API

Validações:

- paginação completa (não parou no meio)?
- respeitou rate limit?
- retries não geraram duplicação?
- checkpoint (cursor) salvo corretamente?

---

## Resumindo

- Validar procedimento de coleta = validar **o processo**, não só os dados.
- O mínimo é checar: **fonte/acesso, completude, consistência, duplicidade, checkpoint e rastreabilidade**.
- Sem logs e metadados, você não prova nada (e BI vira “achismo com gráfico”).
