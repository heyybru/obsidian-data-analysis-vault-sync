Um **índice** é como o **índice de um livro**: em vez de “folhear tudo” (ler a tabela inteira), o banco usa o índice para **achar mais rápido** as linhas que você quer.

Pense assim:

- **Sem índice** = procurar um nome numa lista gigante olhando um por um.
- **Com índice** = usar uma lista “ordenada/organizada” que aponta direto onde está.

✅ Em **RH**: buscar candidato por **email**, filtrar por **vaga**, ordenar por **data**.  
✅ Em **QA**: filtrar bugs por **status/severidade**, buscar por **build_id**, pegar “últimos 7 dias”.

---

## 🔷 Sintaxe

### ✅ Criar índice simples

```sql
CREATE INDEX idx_nome
ON tabela (coluna);
```

### ✅ Criar índice único (impede duplicados)

```sql
CREATE UNIQUE INDEX idx_nome
ON tabela (coluna);
```

### ✅ Criar índice composto (mais de uma coluna)

```sql
CREATE INDEX idx_nome
ON tabela (coluna1, coluna2);
```

### ✅ Criar índice parcial (só para um subconjunto)

```sql
CREATE INDEX idx_nome
ON tabela (coluna)
WHERE condicao;
```

### ✅ Criar índice para busca por texto (PostgreSQL)

```sql
CREATE INDEX idx_nome
ON tabela USING GIN (to_tsvector('portuguese', coluna_texto));
```

### ✅ Apagar índice

```sql
DROP INDEX IF EXISTS idx_nome;
```

---

## 🔷 Passo a passo: quando índice ajuda

Índice costuma ajudar quando você faz muito:

- `WHERE coluna = ...` (filtro por igualdade)
- `WHERE coluna IN (...)`
- `WHERE coluna BETWEEN ... AND ...` (intervalo)
- `ORDER BY coluna` (às vezes)
- `JOIN` por chaves (`... ON a.id = b.id`)

⚠️ Índice **não é de graça**:

- Deixa `INSERT/UPDATE/DELETE` mais lentos (porque precisa atualizar o índice)
- Ocupa espaço

---

## 🔷 Exemplo (RH): índice para acelerar busca de candidato por email

### 1) Cenário

Você sempre faz:

```sql
SELECT *
FROM candidatos
WHERE email = 'bruno@email.com';
```

### 2) Índice ideal (e ainda garante unicidade)

```sql
CREATE UNIQUE INDEX idx_candidatos_email
ON candidatos (email);
```

**Explicando**

- `UNIQUE` garante que **não existam dois candidatos com o mesmo email**
- E acelera buscas por `WHERE email = ...`

## 🔷 Exemplo (QA): índice composto para lista de bugs por status e severidade

### 1) Cenário (bem comum em QA)

```sql
SELECT *
FROM bugs
WHERE status = 'aberto'
  AND severidade IN ('critico', 'alto')
ORDER BY criado_em DESC;
```

### 2) Índice composto (mais útil)

```sql
CREATE INDEX idx_bugs_status_severidade_criado_em
ON bugs (status, severidade, criado_em DESC);
```

**Por que nessa ordem?**

- O banco aproveita melhor quando o índice começa pelas colunas mais usadas no `WHERE` (**status**, depois **severidade**)
- `criado_em DESC` ajuda no “pegar os mais recentes” (muito padrão em triagem)

> ⚠️ Dica prática: índice composto funciona melhor quando a consulta filtra usando o “prefixo” do índice.  
> Ex.: se o índice é `(status, severidade, criado_em)`, ele ajuda muito em:

- `WHERE status = ...`
- `WHERE status = ... AND severidade = ...`  
    Mas pode ajudar menos se você filtrar só por `severidade` ignorando `status`.

## 🔷 Exemplo poderoso: índice parcial (QA) só para bugs abertos

Se 90% dos seus relatórios são “bugs abertos”, você pode indexar **apenas esses**:

```sql
CREATE INDEX idx_bugs_abertos_criado_em
ON bugs (criado_em DESC)
WHERE status = 'aberto';
```

**Por que isso é bom?**

- Índice menor (mais rápido, menos espaço)
- Focado no que você mais consulta

---

## 🔷 Como saber se o índice está sendo usado

Use o plano de execução:

```sql
EXPLAIN ANALYZE
SELECT *
FROM bugs
WHERE status = 'aberto'
ORDER BY criado_em DESC;
```

O que você quer ver:

- ✅ `Index Scan` ou `Bitmap Index Scan` → bom sinal  
    O que costuma ser sinal de “não está usando”:
- ⚠️ `Seq Scan` (varredura completa) em tabela grande

---

## 🔷 Checklist rápido (pra criar índice do jeito certo)

- ✅ Crie índice para colunas muito usadas em **WHERE/JOIN**
- ✅ Para dados únicos (email, CPF, matrícula): use **UNIQUE**
- ✅ Para filtros frequentes em subconjunto: use **índice parcial**
- ⚠️ Não crie índice “em tudo” (vai virar custo sem retorno)
- ✅ Sempre valide com `EXPLAIN ANALYZE`
