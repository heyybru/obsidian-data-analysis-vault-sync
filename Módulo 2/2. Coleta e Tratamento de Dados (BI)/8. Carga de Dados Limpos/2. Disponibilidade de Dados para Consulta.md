“Disponibilidade para consulta” significa que o dado não está só carregado: ele está **encontrável, acessível, rápido e confiável** para quem vai consultar (BI, analistas, cientistas de dados, produto, gestão).

Na prática, você garante isso em 4 pilares: **acesso**, **performance**, **confiabilidade** e **governança**.

---

## 1) Acesso: quem pode consultar e como

Aqui você define:

- **Perfis de acesso (RBAC)**: quem lê o quê (time, área, nível)
- **Dados sensíveis (LGPD/PII)**:
    - mascarar/anonymizar campos quando necessário
    - separar tabelas sensíveis (ex.: dados pessoais) do resto
- **Conexões e ferramentas**:
    - BI (Power BI/Tableau/Looker)
    - SQL (PostgreSQL/BigQuery/Snowflake)
    - notebooks (Python)

👉 Exemplo: analista pode ver agregados, mas não pode ver email/CPF.

---

## 2) Performance: consulta tem que responder no tempo esperado

Mesmo dado correto “não serve” se a consulta leva 10 minutos.

Boas práticas:

- **modelagem** (dimensional, star schema) para BI
- **índices** (em DWs tradicionais)
- **particionamento** (por data, região, entidade)
- **clusterização** (quando o motor suporta)
- **materialized views / tabelas agregadas** para KPIs mais usados

👉 Exemplo: tabela de eventos particionada por `data_evento` melhora consultas por período.

---

## 3) Confiabilidade: o dado está atualizado e consistente

Aqui entram os controles de operação:

- **SLA / freshness**: “atualiza até X horas”
- **monitoramento de pipeline**: falhou? atrasou?
- **reconciliação**: contagens/somas batem com a fonte?
- **versão/ciclo de vida**:
    - o que é “dado oficial”
    - o que é “experimental”

👉 Exemplo: se o dashboard é diário, você precisa monitorar “última atualização” e alertar quando estourar.

---

## 4) Governança: o usuário entende o que está consultando

Disponibilidade também é “entendibilidade”.

Você garante com:

- **catálogo de dados** (descrição de tabelas/colunas)
- **dicionário de métricas** (definição oficial de KPIs)
- **linhagem (lineage)**: fonte → staging → silver → gold
- **data contracts**: regras do dado que chegam das fontes

👉 Exemplo: “Receita líquida” precisa ter definição única, senão cada área calcula de um jeito.

---

## Checks práticos (o que validar para dizer “está disponível”)

- Existe tabela/view “gold” oficial para o tema?
- Está documentada (descrição + dono)?
- Tem permissão correta por perfil?
- Tem partição/índice adequado?
- Tem freshness/SLA monitorado?
- Consultas padrão respondem em < X segundos?

---

## Resumindo

- Disponibilidade para consulta = **acesso + performance + confiabilidade + governança**.
- Não basta carregar: tem que estar **rápido, atualizado, documentado e com permissão correta**.
