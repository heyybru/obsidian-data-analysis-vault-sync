## Introdução

**Restrições de integridade** (ou **constraints**) são regras que garantem que os dados no banco sejam **corretos, consistentes e confiáveis**. Elas **impedem dados inválidos, duplicados ou relacionamentos quebrados** de entrar nas colunas.

🔑 **Analogia:** são como as **regras de um formulário**. Se o campo é "e-mail", o sistema não deixa você digitar um número. As constraints fazem isso no banco — e quem garante é o **SGBD**, não o programador.

**Ponto-chave:** você só configura as constraints na criação (via **DDL**). Depois, o próprio banco passa a fiscalizar os dados automaticamente.

---
## 1. PRIMARY KEY (PK) — identifica

**O que garante:** identifica **unicamente** cada registro.

**Regras:**

- Não pode repetir
- Não pode ser nula

**Quando usar:** em toda tabela, para identificar cada linha de forma única.

**Exemplo em Oracle:**

```sql
id_colaborador NUMBER PRIMARY KEY
```

**Observação:** se tentar inserir uma PK que já existe, o banco **viola a restrição** e recusa.

---

## 2. FOREIGN KEY (FK) — relaciona

**O que garante:** cria o **relacionamento entre tabelas** e garante a **integridade referencial** (todo valor de FK precisa existir como PK).

**Quando usar:** sempre que uma tabela precisar se referir a outra (relacionamentos 1:N, 1:1 ou associativas N:N).

**Exemplo em Oracle:**

```sql
id_departamento NUMBER,
CONSTRAINT fk_departamento
FOREIGN KEY (id_departamento)
REFERENCES departamento(id_departamento)
```

**📌 A FK impede:**

- Inserir colaborador em um **departamento inexistente**
- Excluir um departamento que **ainda tem colaboradores vinculados** (sem regra de exclusão)

**Observação:** na FK é preciso informar a **coluna local**, a **tabela alvo** e a **PK** dela.

---

## 3. NOT NULL — obriga

**O que garante:** o campo **não pode ficar vazio** (nulo).

**Quando usar:** em campos essenciais, que sempre precisam de valor (nome, e-mail, etc.).

**Exemplo em Oracle:**

```sql
nome VARCHAR2(100) NOT NULL
```

**Observação:** está ligado à **cardinalidade mínima** — se a relação é `(1, ...)`, a coluna não pode ser nula; se é `(0, ...)`, pode.

---

## 4. UNIQUE — não repete

**O que garante:** **não permite valores duplicados** na coluna.

**Quando usar:** em campos que devem ser únicos, mas **não são identificadores** da tabela (ex.: RG, e-mail).

**Exemplo em Oracle:**

```sql
email VARCHAR2(100) UNIQUE
```

**⚠️ Diferença da PK:** o `UNIQUE` garante unicidade, mas **não é a chave identificadora** da tabela (e, ao contrário da PK, pode aceitar nulos).

---

## 5. CHECK — valida regras

**O que garante:** valida **regras de negócio simples**, limitando os valores aceitos.

**Quando usar:** em campos com valores restritos ou condições (salário > 0, status em uma lista, etc.).

**Exemplos em Oracle:**

```sql
CHECK (salario > 0)
```

```sql
CHECK (status IN ('A', 'I'))
```

**Observação:** é a restrição de **domínio** — define o tipo e o conjunto de valores válidos para a coluna.

---

## 6. DEFAULT — valor padrão

**O que garante:** define um **valor pré-definido** quando nada é informado.

**Quando usar:** em campos com um valor "natural" de início (status, país, data de cadastro).

**Exemplo em Oracle:**

```sql
status CHAR(1) DEFAULT 'A'
```

**Observação:** está ligado à restrição de **nulo** — se o campo tem `DEFAULT`, ele não fica vazio, recebe o valor padrão.

---

## 🧩 Exemplo Completo (Oracle)

```sql
CREATE TABLE departamento (
  id_departamento NUMBER PRIMARY KEY,
  nome_departamento VARCHAR2(50) NOT NULL
);

CREATE TABLE colaborador (
  id_colaborador NUMBER PRIMARY KEY,
  nome VARCHAR2(100) NOT NULL,
  salario NUMBER CHECK (salario > 0),
  status CHAR(1) DEFAULT 'A',
  id_departamento NUMBER,
  CONSTRAINT fk_colab_depto
    FOREIGN KEY (id_departamento)
    REFERENCES departamento(id_departamento)
);
```

## 📊 Quadro Comparativo das Restrições

|Restrição|Categoria|O que garante|Exemplo|
|---|---|---|---|
|**PRIMARY KEY**|Chave|Registro único e não nulo|`id NUMBER PRIMARY KEY`|
|**FOREIGN KEY**|Referencial|FK sempre aponta para uma PK|`FOREIGN KEY (id) REFERENCES ...`|
|**NOT NULL**|Vazio/Nulo|Campo obrigatório|`nome VARCHAR2(100) NOT NULL`|
|**UNIQUE**|Unicidade|Valor não se repete|`email VARCHAR2(100) UNIQUE`|
|**CHECK**|Domínio|Valida regras/valores|`CHECK (salario > 0)`|
|**DEFAULT**|Valor padrão|Valor pré-definido|`status CHAR(1) DEFAULT 'A'`|

**As 6 categorias de integridade:**

- **Domínio** → tipo e conjunto de valores aceitos (`CHECK`)
- **Vazio/Nulo** → se o campo pode ser vazio (`NULL` / `NOT NULL`)
- **Chave** → PK única e não nula (`PRIMARY KEY`)
- **Referencial** → FK sempre aponta para uma PK (`FOREIGN KEY`)
- **Unicidade** → valor não se repete (`UNIQUE`)
- **Valor padrão** → valor pré-definido (`DEFAULT`)

---

## ⚠️ Restrição Semântica (importante!)

Uma regra que **não se encaixa nos 6 tipos** de restrição deve ser garantida pela **aplicação (software)**, **não pelo banco**.

**Exemplo:** "um funcionário de RH não pode assumir cargo de analista de sistemas" — essa é uma regra de negócio complexa que o banco não consegue validar sozinho. Quem deve tratar é o **programa** que usa o banco.

---

## 🧠 Dica Importante — Onde Criar as Constraints

As restrições podem ser criadas de **duas formas**:

**1️⃣ Na criação da tabela:**

```sql
CREATE TABLE colaborador (
  id_colaborador NUMBER PRIMARY KEY,
  ...
);
```

**2️⃣ Depois, com ALTER TABLE:**

```sql
ALTER TABLE colaborador
ADD CONSTRAINT fk_colab_depto
FOREIGN KEY (id_departamento)
REFERENCES departamento(id_departamento);
```

**💡 Por que dar nome às constraints?** Cada constraint pode (e deve) receber um **nome** (ex.: `fk_colab_depto`, `tipo_pk`). Isso facilita:

- A **manutenção** futura (alterar ou excluir a constraint)
- A leitura de **mensagens de erro** do banco (fica claro qual regra foi violada)

---

## Conclusão

As **restrições de integridade** são a "camada de proteção" do banco de dados. Elas garantem que os dados sejam **corretos, consistentes e confiáveis**, evitando erros antes que eles aconteçam.

**Regra de ouro para memorizar:**

- **PK** identifica · **FK** relaciona · **NOT NULL** obriga
- **UNIQUE** não repete · **CHECK** valida · **DEFAULT** preenche
- **Nunca invente regra no banco** — regras complexas (semânticas) são da aplicação

**Resumindo**

- Constraints são regras garantidas pelo **SGBD**, configuradas via DDL
- São **6 tipos**: PK, FK, NOT NULL, UNIQUE, CHECK e DEFAULT
- Podem ser criadas **na criação da tabela** ou **com ALTER TABLE**
- **Nomear** as constraints facilita manutenção e leitura de erros
- Regras complexas (semânticas) ficam na **aplicação**, não no banco
