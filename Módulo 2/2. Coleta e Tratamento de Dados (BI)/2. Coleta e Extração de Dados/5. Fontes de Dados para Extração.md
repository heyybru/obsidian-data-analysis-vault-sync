Quando você vai montar a fase **Extract**, “fonte de dados” é qualquer lugar de onde você consegue **puxar dados brutos**. O mais importante não é só listar as fontes, mas entender: **como acessar**, **qual o formato**, **se muda com o tempo**, **volume**, e **risco de qualidade/PII**.

---

## 1) Bancos de dados (mais comum em ETL)

### **Relacionais (SQL)**

Ex.: PostgreSQL, MySQL, SQL Server, Oracle

- Melhor para dados estruturados (tabelas, chaves, relacionamentos)
- Extração via SQL/ODBC/JDBC
- Incremental: `updated_at`, `created_at`, `id` crescente

👉 Pontos de atenção:

- locks/performance no transacional
- consistência (snapshot, isolamento)
- tipos de data/hora e timezone

### **NoSQL**

Ex.: MongoDB, DynamoDB, Cassandra

- Dados semiestruturados (documentos)
- Pode exigir “flatten”/normalização depois
- Incremental às vezes por timestamp de atualização

👉 Atenção:

- schema variável
- nested fields (JSON dentro de JSON)

---

## 2) APIs (SaaS e sistemas externos)

Ex.: Jira, Salesforce, HubSpot, ATS, ferramentas de pagamentos

- Retornam JSON
- Exigem autenticação (token/OAuth)
- Quase sempre precisam de paginação

👉 Pontos críticos:

- **rate limit**
- inconsistência eventual
- campos mudando sem aviso
- incremental por cursor/`last_modified`

---

## 3) Arquivos (CSV/Excel/JSON/XML/Parquet)

Fontes típicas:

- export manual (área manda planilha)
- file drop em pasta de rede
- buckets (S3/GCS/Azure Blob)
- FTP/SFTP

👉 Pontos críticos:

- padrão de nomes (ex.: por data)
- encoding (UTF-8 vs ISO)
- separador e decimal (`,` vs `.`)
- Excel com abas/linhas extras/células mescladas
- esquema varia a cada arquivo (colunas a mais/menos)

Boa prática: exigir contrato de arquivo (data contract):

- colunas obrigatórias
- tipos
- frequência
- validações mínimas

---

## 4) Logs e eventos (telemetria)

Ex.: logs de aplicação, clickstream, auditoria, eventos de produto

- Podem ser batch (arquivos) ou streaming (Kafka/PubSub)
- Volume alto e ruído (campos inconsistentes)

👉 Pontos críticos:

- duplicidade de eventos
- ordenação temporal
- schema evolution (mudanças no formato)
- necessidade de dedupe por `event_id`

---

## 5) Streaming / mensageria (near real-time)

Ex.: Kafka, Kinesis, Pub/Sub, RabbitMQ

- Fonte contínua, baseada em eventos
- Ideal para pipelines rápidos e reatividade

👉 Pontos críticos:

- exactly-once vs at-least-once (duplicatas)
- checkpoints/offsets
- retenção e replay (reprocessamento)

---

## 6) Dados externos / públicos / terceiros

Ex.: IBGE, dados abertos governamentais, provedores de mercado

- Pode ser API ou arquivo
- Usado para enriquecer análises

👉 Pontos críticos:

- licença de uso
- atualização e defasagem
- confiabilidade/metadata

---

## 7) Como escolher a estratégia de extração por fonte (regra rápida)

- **DB relacional** → incremental por `updated_at` / CDC (se necessário)
- **API** → paginação + cursor + retries + rate limit
- **Arquivos** → particionar por data + controle de versões + validação de schema
- **Logs/streaming** → offsets + dedupe + schema registry (quando existir)

---

## 8) Checklist curto “por fonte” (pra você mapear certo)

Para cada fonte, responda:

- O dado é **imutável** (evento) ou **mutável** (cadastro)?
- Existe **ID único**? (pra deduplicar e fazer upsert)
- Existe `updated_at` confiável?
- Qual o **volume** e a **frequência**?
- Tem **PII/LGPD**? (nome, email, doc)
- Qual a **forma de acesso** e credenciais?
- Quais os riscos (rate limit, schema variável, manual)?

---

## 📋 Resumindo

- Fontes para extração geralmente caem em: **bancos**, **APIs**, **arquivos**, **logs/eventos**, **streaming** e **dados externos**.
- A melhor extração depende de: **imutável vs mutável**, **ID**, **updated_at**, **volume**, **limites**, **qualidade** e **PII**.
