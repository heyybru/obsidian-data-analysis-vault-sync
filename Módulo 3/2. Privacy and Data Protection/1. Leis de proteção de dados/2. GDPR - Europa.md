## 🇪🇺 Pilares Estratégicos do GDPR

Diferente de leis anteriores, o GDPR foca na **Responsabilização (Accountability)**. Não basta cumprir; a empresa deve provar que cumpre através de documentação e auditorias constantes.

- **Privacy by Design & Default**: A proteção deve ser nativa no sistema. No seu trabalho de QA, isso significa que a privacidade é um requisito funcional desde o primeiro dia de desenvolvimento.
- **Base Legal**: O tratamento de dados só existe se houver uma justificativa (Consentimento, Contrato, Interesse Legítimo, etc.).
- **Minimização**: Coletar apenas o estritamente necessário. Segundo a **Snaq.co**, reduzir o volume de dados coletados diminui drasticamente a superfície de ataque em caso de vazamento.

## 🧪 Aplicação Técnica: Pseudonimização

A **AILabs** reforça que a **Pseudonimização** é a técnica recomendada pelo GDPR para análise de dados. Ela separa a identidade do dado (ex: substitui o nome por um ID único), permitindo que você treine modelos de Machine Learning ou rode testes de QA sem expor o titular diretamente.

- **Diferença Crucial**: Dados pseudonimizados ainda são dados pessoais (podem ser revertidos com uma chave). Dados **anonimizados** não são mais dados pessoais (reversão impossível) e saem do escopo do GDPR.

## 🛠️ Automação de Proteção com Python

No seu dia a dia de QA e Dados, você pode automatizar o mascaramento de dados sensíveis para garantir que os logs de teste não violem o GDPR:

``` 
def mask_email(email):
    """
    Masks an email address for data protection.
    Example: 'bob@gmail.com' -> 'b**@gmail.com'
    """
    if '@' not in email:
        return email
    local, domain = email.split('@', 1)
    if len(local) > 1:
        masked_local = local[0] + '*' * (len(local) - 1)
    else:
        masked_local = local
    return f'{masked_local}@{domain}'

Example usage for QA log simulation:
email = 'bob@gmail.com'
masked = mask_email(email)
print(f'Original: {email}')
print(f'Masked: {masked}')
```
